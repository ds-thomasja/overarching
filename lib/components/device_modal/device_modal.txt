h2. User Story

As a clinician working in an environment with multiple connected devices, I want to select a specific device from a list quickly and with minimal interaction, so that I can proceed with my clinical task without workflow interruption.

----

h2. Design Definition & Assets

* *Figma Link:* [DeviceModal|https://www.figma.com/design/oY2AELOxR8s6HKYkCTAOQs/Equipment-Components?node-id=5098-5219]
* *Flutter Component:* TBD — the version on {{origin/main}} does not match this specification. {{device_modal.dart}} exists at {{overarching/lib/components/device_modal/device_modal.dart}}; the pushed commits ({{7b15355}}, {{2b06353}}, {{2761260}}) are on {{origin/main}}, but the working tree has further uncommitted local changes on top — including the entire {{selectionRequiredMessage}} validation-notification behavior this document describes — so a link to the current {{origin/main}} blob would show an outdated API. Re-check once those changes are committed and pushed.
* *Interaction Model:* {{DeviceModal}} exposes two named constructors that produce structurally different content, chosen by which one the caller invokes rather than by a boolean flag. {{DeviceModal.selectDevice}} renders one {{DeviceCard}} per {{devices}} entry plus a primary footer button (default label "Confirm"). When {{selectable}} is {{true}} (the default), tapping a card only moves a pending selection highlight that the widget owns internally; only pressing the primary button — via {{onConfirm}} — commits that selection, passing its index. Pressing it with nothing selected shows {{selectionRequiredMessage}} as an informational notification in place of {{notificationMessage}} until a card is picked or that notification is dismissed. When {{selectable}} is {{false}} ("one-click" list), there is no footer button at all — tapping any card calls {{onConfirm}} immediately with its index, and {{confirmLabel}}/{{selectionRequiredMessage}} are unused. {{DeviceModal.deviceDetails}} instead renders one focused {{DeviceModalDeviceDetails}} (its {{name}} doubling as the modal title), an info row of sublines/battery/status, a fixed 240×240 image slot, an optional segmented control ({{segments}}), an optional inline notification, and then either an optional progress card ({{progress}}, an indeterminate or determinate {{DSProgressBar}} plus a label) or a switchable list of {{otherDevices}} rendered as {{DeviceCard}}s — {{progress}} and that list are alternate states of the same area, not simultaneous: whenever {{progress}} is set the list is suppressed regardless of what {{otherDevices}} contains. Tapping a switchable device card calls {{onOtherDeviceSelected}} with its index (those cards never show a selection highlight); a secondary footer button (default label "Switch device") calls {{onSwitchDevice}}. In both modes, pressing the header close icon-button calls {{onClose}} — the caller is responsible for actually dismissing the modal (typically the {{pop}} callback from {{showDSModalDialog}}); passing the DS {{hideDialogCloseButton}} sentinel as {{onClose}} removes the close button entirely. {{DeviceModal}} is not itself a route: it must be shown via {{showDSModalDialog}}, which supplies the dimmed barrier, centered alignment, route and inherited themes.

h2. Component Props

{{DeviceModal}} has no single flat prop list — its two named constructors take different prop sets for their structurally different content (see Interaction Model above). Three supporting data classes carry the per-device and per-progress information: {{DeviceModalDevice}} (one row in either device list), {{DeviceModalDeviceDetails}} (the single focused device in details mode) and {{DeviceModalProgress}} (the details-mode progress card).

h2. Acceptance Criteria

 - *Functional:*
 -- {{DeviceModal.selectDevice}} and {{DeviceModal.deviceDetails}} are the only two entry points — there is no runtime flag that toggles between their content shapes
 -- In select mode, when {{selectable}} is {{true}} (default), tapping a card only moves the pending selection highlight; {{onConfirm}} fires only when the primary button is pressed, with the selected index
 -- In select mode, when {{selectable}} is {{false}}, tapping a card calls {{onConfirm}} immediately with that card's index; no footer button renders, and {{confirmLabel}}/{{selectionRequiredMessage}} are unused
 -- Pressing the primary button with no card selected shows {{selectionRequiredMessage}} (default "Please select a device before continue") as an informational notification in place of {{notificationMessage}}, and does not call {{onConfirm}}; selecting a card or dismissing that notification restores {{notificationMessage}}
 -- {{initiallySelectedIndex}} seeds the pending selection once, on first build, in select mode; later prop changes are ignored once the widget owns the selection
 -- If {{devices}} shrinks below the currently selected index, the selection is cleared rather than pointing at a stale/out-of-range index
 -- In details mode, tapping an {{otherDevices}} card calls {{onOtherDeviceSelected}} with its index when non-null; those cards never show a selection highlight themselves
 -- In details mode, the secondary button calls {{onSwitchDevice}} and is disabled when it is null
 -- The details-mode info row renders only when at least one of {{subline1}}, {{subline2}}, {{batteryPercent}}, {{status}} is non-null; present items are separated by a "·" divider, in that fixed order
 -- The details-mode image renders {{image}} when supplied, else a plain placeholder box, at a fixed 240×240 square, centered
 -- The details-mode segmented control renders only when {{segments}} is non-empty; each label doubles as its own value (must be unique, enforced by an assertion), and every segment renders fully disabled — not merely inert — when {{onSegmentChanged}} is null
 -- The details-mode progress card renders only when {{progress}} is non-null; a null {{DeviceModalProgress.value}} yields an indeterminate bar, otherwise the bar shows {{value}} (0.0–1.0)
 -- Whenever {{progress}} is non-null, the details-mode switchable device list is suppressed entirely, regardless of what {{otherDevices}} contains
 -- The inline notification (both modes) shows {{notificationMessage}} with {{notificationType}} styling and calls {{onNotificationClose}} on its own close control; it is hidden entirely when {{notificationMessage}} is null
 -- The modal title truncates to 1 line with an ellipsis in both modes; in details mode it always equals the focused device's {{name}}
 -- Pressing the header close icon-button always calls {{onClose}}; passing the DS {{hideDialogCloseButton}} sentinel as {{onClose}} removes the close button entirely

 - *States:*
 -- Device rows inherit {{DeviceCard}}'s complete state set (default/hover/pressed/focus/selected/disabled) unchanged — see [DeviceCard|../device_card/device_card.txt] Acceptance Criteria → States
 -- Segmented control segments follow {{DSSegmentedControl}}'s own selected/enabled states; a segment is disabled outright, not merely non-interactive, when {{onSegmentChanged}} is null
 -- Progress bar: indeterminate (animated) when {{DeviceModalProgress.value}} is null; determinate otherwise
 -- Close icon-button, primary and secondary footer buttons follow {{DSButton}}'s own tertiary/primary/secondary state sets respectively

 - *A11y:*
 -- The title is a plain {{Text}}, not {{DSText}} — a truncated title has no hover tooltip (deliberate trade-off; see Content Logic & Edge Cases)
 -- The "·" divider glyphs are excluded from the semantics tree ({{ExcludeSemantics}}), both in the details info row and (via {{DeviceCard}}) in device rows
 -- The details-mode image is excluded from semantics, since it conveys nothing the title/info row don't already state
 -- Close icon-button and footer buttons are standard {{DSButton}} instances, inheriting their built-in keyboard/focus/ARIA behavior
 -- Device rows inherit {{DeviceCard}}'s own accessibility behavior (button semantics, focus, keyboard activation)

h2. Content Logic & Edge Cases

* *Two named constructors, not one boolean:* the Figma node's single {{details}} boolean selects two structurally different content shapes with different data needs; the component exposes them as {{DeviceModal.selectDevice}} and {{DeviceModal.deviceDetails}} instead of a shared API with everything optional.
* *Selection is modal-owned, not caller-owned:* unlike {{DeviceCard.selected}} (a caller-driven prop) or DS toggle widgets, the pending selection in select mode lives inside {{DeviceModal}}'s own state and is only surfaced via {{onConfirm}} on commit — hoisting a selection that gets discarded on close would buy the caller nothing.
* *Progress vs. device list mutual exclusion:* {{progress}} and the switchable {{otherDevices}} list in details mode are alternate states of one area, not simultaneous — when {{progress}} is set, the list is hidden regardless of its contents, so a caller driving both off one "is loading" flag never has to remember to clear the list separately.
* *Header-to-body gap breaks from {{DSModalDialog}}:* {{DSModalDialog}} hard-codes 24px above and below its body with no override; the Figma node wants 0 in details mode and 16px in list mode. Since {{spacing.layout.m}} also drives the surface's own padding (which Figma does want at 24), there is no token-only fix. The surface is therefore hand-rebuilt token-for-token as {{_DeviceModalSurface}} rather than wrapping {{DSModalDialog}} directly — the one deliberate place Figma spacing wins over DS chrome, at the cost of this surface duplicating (and being able to drift from) {{DSModalDialog}}'s own arrangement.
* *240px image slot is not token-derived:* the Figma node specifies a fixed 240×240 slot; DS v51.0.0's only matching size token ({{image.size.card}}, 128/64) is meant for card thumbnails, so the value is kept as a literal constant to be replaced if DS ever introduces a matching token.
* *No DS non-interactive bordered card exists:* the progress card's outline is hand-built from {{border.standard}}/{{border.width.standard}}/{{surface.standard}} tokens directly, because DS v51.0.0 has no non-interactive bordered card ({{DSContainer}} has no border; {{DSSpaciousCard}} is an interactive surface).
* *Plain {{Text}} for the title, not {{DSText}}:* the Figma details variant ellipsis-truncates the device name, which {{DSModalDialog}}'s own unbounded {{Text}} could not do; a plain {{Text}} keeps the title's color resolving through the ambient {{DefaultTextStyle}} exactly as before, at the cost of no hover tooltip on a truncated title.
* *Stale selection guard:* if {{devices}} shrinks (e.g. a filtered list) below the currently pending selected index, the selection is cleared on the next build rather than risking a stale index ever reaching {{onConfirm}}.
* *"One-click" list has no footer at all:* when {{selectable}} is {{false}}, there is no footer button and therefore no {{bodyBottomGap}} below the body — only the surface's own vertical padding remains below the last card.
* *Figma's {{scrollbar}} boolean has no equivalent:* {{DSCustomScrollView}} always scrolls the body and always shows the real DS hover-visible scrollbar, so there is nothing in this component to toggle for it.
* *Device rows reuse the real {{DeviceCard}}, stretched:* rows render at {{width: double.infinity}} rather than {{DeviceCard}}'s own 438px default, so they keep filling the modal's content width if the DS modal narrows on a smaller form factor or the scrollbar gutter takes width away; at the Figma modal width (486 − 2×24 padding) both numbers coincide.
* *{{status}} defaults to null, not {{DeviceCard}}'s own {{online}} default:* {{DeviceModalDevice}}/{{DeviceModalDeviceDetails}} describe data, and a device whose connectivity is not stated should not claim to be online; this also makes the name/subline-only card of the Figma details mode the zero-configuration case.
* *Variant defaults to {{DSModalDialogVariant.small}}:* this is the DS variant whose width resolves to 486 at the extra-large form factor, matching the Figma node exactly; other {{variant}} values are accepted and use their own DS responsive widths.
